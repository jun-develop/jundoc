Why does Fx exist?Vì sao cần Uber Fx?

A production backend is composed of many interdependent layers: Config, Database, Repository, Service, Handler... Someone must initialize them in the exact right order and inject the right dependencies.

Một backend hoàn chỉnh gồm nhiều tầng phụ thuộc lẫn nhau: Config, Database, Repository, Service, Handler... Cần một cơ chế khởi tạo chúng đúng thứ tự và tự động truyền đúng thành phần vào nơi cần.

Without Fx — everything is dumped into main.goKhi chưa có Fx — dồn toàn bộ vào main.go (Dài dòng & Dễ xung đột)

cmd/api/main.go (All features dumped into 1 file)
// 1. Core infrastructure
cfg := config.NewConfig()
db, _ := primary.New(lc, sqlLogger, cfg)

// 2. Feature User: manual constructor calls and hand-offs
userRepo    := repository.NewUserRepository(db)
userSvc     := service.NewUserService(userRepo, storage, hasher, …)
userHandler := v1handler.NewUserHandler(userSvc, responder, …)
userRoutes  := v1route.NewUserRoutes(userHandler, …)

// 3. Feature Product: manual wiring continues
productRepo    := repository.NewProductRepository(db)
productSvc     := service.NewProductService(productRepo, userSvc, …)
productHandler := v1handler.NewProductHandler(productSvc, responder, …)
productRoutes  := v1route.NewProductRoutes(productHandler, …)

// 4. Register all routes onto router
router.RegisterAll(engine, userRoutes, productRoutes, …)

// ❌ Consequence: Adding 10-20 more features bloats main.go to hundreds of lines!
// Every change touches main.go -> Frequent Git merge conflicts!
cmd/api/main.go (Tất cả feature dồn vào 1 file duy nhất)
// 1. Hạ tầng cơ sở
cfg := config.NewConfig()
db, _ := primary.New(lc, sqlLogger, cfg)

// 2. Feature User: phải tự tay gọi từng hàm và truyền biến
userRepo    := repository.NewUserRepository(db)
userSvc     := service.NewUserService(userRepo, storage, hasher, …)
userHandler := v1handler.NewUserHandler(userSvc, responder, …)
userRoutes  := v1route.NewUserRoutes(userHandler, …)

// 3. Feature Product: lại tiếp tục tự tay khởi tạo từng món
productRepo    := repository.NewProductRepository(db)
productSvc     := service.NewProductService(productRepo, userSvc, …)
productHandler := v1handler.NewProductHandler(productSvc, responder, …)
productRoutes  := v1route.NewProductRoutes(productHandler, …)

// 4. Đăng ký tất cả routes lên router
router.RegisterAll(engine, userRoutes, productRoutes, …)

// ❌ Hậu quả: Thêm 10-20 features nữa, main.go sẽ phình to hàng trăm dòng!
// Ai sửa gì cũng đụng vào main.go -> Rất dễ xung đột Git merge!
Manual Chain:Dồn hết vào 1 file duy nhất: Everything wired manually in main.go. Error-prone order, huge fragile file. Mọi feature đều dồn hết vào main.go. Dễ sai thứ tự, file phình to và rất dễ xung đột git merge.

With Fx — Each feature is self-contained in its moduleCó Fx — Mỗi feature tự đóng gói riêng, fx.go chỉ việc gọi

internal/features/user/module.go (User Feature Module)
var Module = fx.Module("user",
    fx.Provide(fx.Annotate(repository.NewUserRepository, // Fx injects DB
        fx.As(new(domain.UserRepository)))),
    fx.Provide(fx.Annotate(service.NewUserService,       // Fx injects Repo
        fx.As(new(domain.UserService)))),
    fx.Provide(v1handler.NewUserHandler),                // Fx injects Svc
    fx.Provide(fx.Annotate(v1route.NewUserRoutes,        // Fx injects Handler
        fx.As(new(router.Routes)), fx.ResultTags(`group:"routes"`))),
    // … console commands + fx.Invoke(registerTranslations)
)
internal/features/product/module.go (Product Feature Module)
var Module = fx.Module("product",
    fx.Provide(fx.Annotate(repository.NewProductRepository, // Fx injects DB
        fx.As(new(domain.ProductRepository)))),
    fx.Provide(func(opts cache.Options) cache.Cache[*domain.Product] {
        return cache.New[*domain.Product](opts)
    }),
    fx.Provide(fx.Annotate(service.NewProductService,       // Fx injects ProductRepo & cache
        fx.As(new(domain.ProductService)))),
    fx.Provide(v1handler.NewProductHandler),                // Fx injects ProductSvc
    fx.Provide(fx.Annotate(v1route.NewProductRoutes,        // Fx injects ProductHandler
        fx.As(new(router.Routes)), fx.ResultTags(`group:"routes"`))),
    fx.Invoke(registerTranslations),
)
internal/app/fx.go (Plug modules into app — clean & modular)
fx.New(
    fx.Supply(cfg), // Supplies Config to DB and services
    primary.Module,
    user.Module,    // Clean: Just 1 line for the entire User feature!
    product.Module, // Clean: Just 1 line for the entire Product feature!
    fx.Invoke(router.RegisterAll),
).Run()

Modular & Clean:Gọn gàng & Độc lập: Each feature manages its own constructors. fx.go only adds 1 clean line per feature. Feature nào tự quản lý trong module của feature đó. File fx.go luôn tinh gọn, chỉ 1 dòng/feature!
⭐ IMPORTANT: Why we need Fx — Modular Architecture & Zero Vendor Lock-in! LƯU Ý CỰC KỲ QUAN TRỌNG: Vì sao cần Fx — Kiến trúc Module gọn gàng & Code Go thuần 100%!

1. Why Fx is essential: Without Fx, every single service and repository across all features (User, Product, Order...) must be wired line-by-line inside main.go. With 20+ features, main.go becomes a massive, fragile bottleneck where every team member edits the same file, causing endless git merge conflicts. With Fx, each feature packages its own dependencies inside its own directory (user/module.go, product/module.go), and fx.go only needs a single line per module!

1. Lý do vì sao bắt buộc cần Fx: Nếu không có Fx, mọi linh kiện của tất cả feature (User, Product, Order...) đều bị dồn hết vào main.go. Khi app có 20-30 feature, main.go sẽ biến thành một "nút thắt cổ chai" khổng lồ, ai làm tính năng gì cũng phải vào sửa main.go gây conflict git liên miên. Với Fx, mỗi feature tự gói gọn gàng bên trong thư mục của nó (user/module.go, product/module.go), và file fx.go chỉ cần gọi đúng 1 dòng tên module!

2. Inside business code, nothing changes: In your actual Go files (Service, Repository, Handler), you still write standard Go structs, interfaces, and methods as usual — zero Fx imports, zero container.Get() calls. The only difference is where wiring happens: main.go manual hand-off vs. cleanly isolated module.go files!

2. Trong ruột code Go thì vẫn viết như cũ: Bên trong các file nghiệp vụ (Service, Repository, Handler), bạn vẫn viết struct, interface và method bình thường như cũ 100% — tuyệt đối không import Fx, không có bất kỳ lệnh container.Get() nào. Điểm khác biệt duy nhất chỉ là nơi kết nối: thay vì dồn hết vào main.go thủ công thì mỗi feature tự gói vào module.go của chính nó!

💡 Explained for Beginners: What is Dependency Injection (DI)? Giải thích siêu dễ hiểu: Dependency Injection (DI) thực chất là gì?

Forget the complicated academic jargon. Dependency Injection is just a fancy name for one simple rule: "Never create what you need inside a function — ask for it through parameters instead."

Đừng để những thuật ngữ học thuật làm bạn bối rối. Dependency Injection thực chất chỉ là một cái tên phức tạp cho một nguyên tắc cực kỳ đơn giản: "Hàm cần dùng cái gì thì nhận qua tham số — tuyệt đối không tự tạo bên trong ruột hàm."

❌ Without DI: Self-creating inside ❌ KHÔNG dùng DI: Tự tạo đồ bên trong 
func NewUserService() *UserService {
    // Creates DB internally -> tightly coupled forever!
    db, _ := primary.New(...)
    return &UserService{db: db}
}
func NewUserService() *UserService {
    // Tự new DB -> Bị dính chặt vĩnh viễn!
    db, _ := primary.New(...)
    return &UserService{db: db}
}

You cannot test this service with a mock database without editing the code.

Hậu quả: UserService bị dính chặt cố định vào DB thật đó. Bạn không thể viết Unit Test với Mock DB nếu không sửa lại mã nguồn.

✅ With DI: Injected via parameter ✅ CÓ dùng DI: Đưa vào qua tham số 
// Simply accepts DB from outside via parameter
func NewUserService(db *primary.DB) *UserService {
    return &UserService{db: db}
}
// Chỉ xòe tay nhận DB từ bên ngoài
func NewUserService(db *primary.DB) *UserService {
    return &UserService{db: db}
}

Extremely flexible! Pass a real DB in production, or pass a fake/mock DB in tests.

Lợi ích: Cực kỳ linh hoạt! Khi chạy app thật thì đưa DB thật, khi viết test kiểm thử thì đưa Mock DB vào.

So what is Uber Fx (DI Container)?Vậy Uber Fx (DI Container) giải quyết bài toán gì?
When your app grows to 50+ services, manually passing db into repo, repo into service, service into handler inside main.go becomes a nightmare. Uber Fx is like an automated warehouse robot: you simply register your constructors, and Fx automatically inspects their parameters, finds what each function needs, creates them in the exact right order, and passes them in for you. Khi ứng dụng lớn lên có hàng chục Service và Handler, việc bạn phải tự tay gõ từng dòng để truyền db vào repo, repo vào service, service vào handler trong main.go sẽ biến thành một cơn ác mộng. Uber Fx giống như một "Robot lắp ráp tự động": Bạn chỉ việc đăng ký các hàm tạo, Fx sẽ tự nhìn vào tham số của từng hàm, tự tìm món đồ hàm đó cần, khởi tạo đúng thứ tự từ trước ra sau rồi tự đưa vào giúp bạn.

Core principle: Dependencies & ProvidesNguyên lý cốt lõi: Đầu vào cần nhận & Sản phẩm tạo ra

Everything in Fx is built on this single concept. Look at any constructor in Jungo:

Bản chất của Fx chỉ xoay quanh 2 điều: Hàm này cần gì (tham số) và Hàm này làm ra món gì (giá trị trả về). Nhìn vào constructor bất kỳ trong Jungo:

DependenciesDependencies (Cần) = ParametersTham số đầu vào

What the service requires to operate. Fx automatically finds and passes each one into the constructor. Những thứ bắt buộc phải có để hoạt động. Fx sẽ tự tìm đúng món đồ trong hệ thống để truyền vào hàm giúp bạn.
func NewUserService( repo domain.UserRepository, storage storage.Service, … ) *UserService

ProvidesProvides (Cung cấp) = Return valueGiá trị trả về

What the constructor creates. Fx stores it and injects it into any other component that requests it. Món đồ do hàm tạo ra. Fx sẽ lưu lại và tự động mang đi cấp phát cho bất kỳ hàm nào khác cần dùng đến nó.
1

Constructor is standard GoConstructor là hàm Go thuần túy

Input = parameters. Output = return value. A plain Go function without any Fx-specific dependencies inside.

Đầu vào = tham số. Đầu ra = giá trị trả về. Đây là hàm Go tiêu chuẩn, không dính bất kỳ thư viện Fx nào bên trong, cực kỳ dễ viết Unit Test.

2

Register with fx.ProvideĐăng ký "công thức" với fx.Provide

fx.Provide(NewUserService) tells Fx: "here is how to construct a UserService". Registration is that simple.

fx.Provide(NewUserService) chỉ đơn giản là báo cho Fx: "đây là công thức để tạo ra UserService". Đăng ký chỉ cần 1 dòng như vậy.

3

Fx connects the puzzle piecesFx tự ráp nối các mảnh ghép

It matches parameter types to return types, invokes constructors in topological order, and ensures each is built at most once (Singleton).

Fx tự so khớp: hàm nào cần món gì thì Fx tìm hàm tạo ra món đó để gọi trước. Mỗi món chỉ tạo duy nhất 1 lần (Singleton) rồi dùng chung toàn app.

fx.Provide(NewX) = Lazy Provider (Cookbook)= Đăng ký công thức (Lazy)

X is only constructed if another component requires it. Once created, the same instance is shared app-wide.

Chưa tạo ngay! Fx chỉ ghi nhớ công thức. Khi nào có nơi khác cần dùng X thì Fx mới gọi hàm tạo, và dùng chung 1 đối tượng duy nhất (Singleton).

fx.Invoke(fn) = Eager Execution (Start Button)= Nút bấm khởi động (Eager)

Always executed at startup. Whatever fn requires will be constructed first — this triggers the entire startup chain.

Chạy ngay lập tức khi app bật lên (ví dụ: gắn route, bật server). Mọi thứ mà hàm này cần sẽ thúc đẩy Fx đi tìm và khởi tạo trước.

💡 The Handoff Principle: How "Provides" delivers directly into "Needs" 💡 Cơ chế chuyển giao: Cái "Cung cấp" gửi thẳng sang cái "Cần"

Every component is declared as a constructor function:
• Row NEEDS: The input parameters requested by the function.
• Row PROVIDES: The return value created by that function.
Fx analyzes the graph and automatically takes the return value from a Provider's output ➔ injects it into the receiver's input parameter!
👉 Hover over any pill below (e.g. *UserHandler) to see the exact Provider-to-Receiver link light up!

Mỗi thành phần trong Fx thực chất là một hàm Constructor:
• Dòng CẦN: Là các tham số hàm đòi hỏi đầu vào.
• Dòng CUNG CẤP: Là kết quả trả về của hàm đó.
Fx phân tích đồ thị và tự động lấy kết quả ở dòng "Cung cấp" của hàm này ➔ gửi thẳng vào dòng "Cần" của hàm tiếp theo mà bạn không cần tự tay gõ lệnh truyền biến!
👉 Rê chuột vào bất kỳ ô nào bên dưới (ví dụ: *UserHandler) để thấy đường truyền từ Cung cấp sang Cần sáng bừng lên!

How Fx thinks: Plan backwards ➔ Build forwardsCách Fx tư duy: Lên kế hoạch ngược ➔ Bắt tay làm xuôi
Fx plans what to do backwards (Top-Down: starting from the startup trigger Invoke, it traces who provides each parameter until reaching the root config). Then it creates objects forwards (Bottom-Up: building root config first, then DB, then services, and finally starting the server). You never need to manually order lines of code again! 1. Cứ hỏi ngược dần cho tới khi chạm đến gốc rễ là file cấu hình *config.Config.
2. Lúc bắt tay khởi tạo (Làm xuôi từ gốc lên ngọn): Fx tạo Config ➔ mở kết nối DB ➔ tạo Repo ➔ tạo Service ➔ tạo Handler ➔ tạo Routes ➔ Bật Server!
Bạn không bao giờ phải tự tay xếp thứ tự từng dòng code nữa! Fx tự nhìn kiểu dữ liệu của tham số để biết ai phải được sinh ra trước ai.

Resolves dependency graph and runs Invokes.

Hooks execute in order: HTTP server starts listening.

When Fx reports an errorKhi Fx báo lỗi lúc khởi động — Cách đọc & Sửa nhanh

Fx validates every dependency its Invokes reach (directly or indirectly) before running — an unused provider with a missing dependency goes unnoticed. If something is missing or misconfigured, it halts immediately with clear diagnostics.

Fx kiểm tra mọi linh kiện mà các Invoke cần tới (trực tiếp hoặc gián tiếp) ngay khi vừa bật ứng dụng — provider không ai dùng mà thiếu dependency thì sẽ không bị phát hiện. Nếu phát hiện thiếu linh kiện hoặc lắp ngược, nó sẽ dừng ngay lập tức kèm thông báo lỗi rất rõ ràng:

missing type: X

A constructor requires X, but no provider in the container produces X.

Một hàm yêu cầu nhận kiểu dữ liệu X, nhưng trong container chưa có Provider nào đăng ký cung cấp kiểu X.

→ Add fx.Provide(NewX), or add its module to fx.go. Check that fx.As matches the interface requested by the caller.

→ Thêm fx.Provide(NewX) hoặc nạp module của nó vào fx.go. Nếu có dùng fx.As, hãy đảm bảo interface chỉ định khớp chính xác với kiểu mà nơi nhận đang đòi hỏi.

cycle detected

Circular dependency: A requires B and B requires A (directly or indirectly).

Vòng lặp con gà & quả trứng: Component A đòi có B mới tạo được, nhưng B lại đòi phải có A mới tạo được (trực tiếp hoặc gián tiếp).

→ Move shared logic to a separate component, or decouple via a smaller interface.

→ Tách phần logic dùng chung ra một struct/service thứ ba, hoặc cho một bên phụ thuộc vào một interface nhỏ hơn để phá vỡ vòng lặp.

already provided

Two providers produce the exact same type without distinguishing tags.

Xung đột trùng lặp: Có 2 hàm Provider khác nhau cùng đăng ký tạo ra một kiểu dữ liệu mà không có nhãn phân biệt, khiến Fx không biết phải chọn cái nào.

→ Remove one duplicate provider, or differentiate them using a name tag or group. Two databases are the exception: give each its own type (*primary.DB, *analytics.DB) instead of a tag.

→ Xóa bớt 1 Provider bị trùng, hoặc nếu cố tình tạo 2 cái (ví dụ 2 logger) thì hãy gắn nhãn phân biệt bằng tag name hoặc gom vào group. Riêng 2 database thì ngoại lệ: mỗi database có một kiểu riêng (*primary.DB, *analytics.DB) thay vì dùng tag.
