Multiple databasesNhiều database

Jungo runs on one PostgreSQL database today. The code is laid out so a second one — another Postgres or a different engine — plugs in without editing the repositories you already have, and the compiler stops a repository from talking to the wrong database.

Hiện tại Jungo chạy trên một database PostgreSQL. Code được tổ chức sẵn để thêm database thứ hai — một Postgres khác hoặc một engine khác — mà không phải sửa các repository đang có, và compiler sẽ chặn một repository dùng nhầm database.

LayoutCấu trúc thư mục

Databases are named by role in jungo (primary, analytics). Engines are named by engine in junkit (postgres, mysql).

Trong jungo, database được đặt tên theo vai trò (primary, analytics). Trong junkit, package được đặt tên theo engine (postgres, mysql).

How a repository picks its databaseRepository chọn database như thế nào

No name: tags, no string keys. The Go type is the choice.

Không cần tag name:, không cần key dạng chuỗi. Kiểu Go chính là lựa chọn.

1

A distinct type per database. primary.DB embeds *postgres.DB. A repository that declares db *primary.DB can only be given the primary database — Fx and the compiler refuse anything else.

Mỗi database một kiểu riêng. primary.DB nhúng *postgres.DB. Repository khai báo db *primary.DB thì chỉ nhận được database chính — Fx và compiler từ chối mọi thứ khác.

2

Queries(ctx) is bound to that database's sqlc package. primary.DB.Queries returns *primary/sqlc.Queries, so you can't call another database's queries on it.

Queries(ctx) gắn với package sqlc của chính database đó. primary.DB.Queries trả về *primary/sqlc.Queries, nên không thể gọi query của database khác trên nó.

3

The transaction key is per DB instance. A transaction begun on one database is never picked up by another database's Executor(ctx).

Key transaction riêng cho từng DB instance. Transaction mở trên database này không bao giờ bị Executor(ctx) của database khác dùng nhầm.

Transactions across databasesTransaction giữa nhiều database

One WithTransaction covers one database. Writes to two databases are never atomic.

Một WithTransaction chỉ bao một database. Ghi vào hai database thì không bao giờ atomic.

1

Calling another database's repository inside txCtx is safe — it runs on its own pool, never on this transaction. But it is not part of the transaction: if this one rolls back, that write stays.

Gọi repository của database khác bên trong txCtx là an toàn — nó chạy trên pool riêng, không bao giờ chạy trên transaction này. Nhưng nó không thuộc transaction: nếu transaction này rollback, lần ghi kia vẫn còn.

2

Need both writes to happen? Write an outbox row in the same transaction as the main data, then let a worker apply it to the other database asynchronously (with retries).

Cần cả hai lần ghi đều xảy ra? Ghi một dòng outbox trong cùng transaction với dữ liệu chính, rồi để worker áp dụng sang database kia một cách bất đồng bộ (có retry).

service
err := s.repo.WithTransaction(ctx, func(txCtx context.Context) error {
	if err := s.repo.Create(txCtx, order); err != nil {
		return err
	}
	// same database: commits or rolls back with the order
	return s.repo.AddOutboxEvent(txCtx, event)
})

// a worker later reads the outbox and writes to analytics
service
err := s.repo.WithTransaction(ctx, func(txCtx context.Context) error {
	if err := s.repo.Create(txCtx, order); err != nil {
		return err
	}
	// cùng database: commit hoặc rollback cùng với order
	return s.repo.AddOutboxEvent(txCtx, event)
})

// sau đó worker đọc outbox và ghi sang analytics

Checklist: a different engineChecklist: thêm engine khác

First a new package junkit/database/<engine>, modelled on database/postgres. Then the jungo side is the same as section 5.

Trước tiên là package mới junkit/database/<engine>, làm theo mẫu database/postgres. Sau đó phía jungo làm giống mục 5.

1

Executor only. Queries run through Executor(ctx); expose Ping(ctx) for health checks, not the raw pool.

Chỉ qua Executor. Query chạy qua Executor(ctx); cung cấp Ping(ctx) cho health check, không lộ pool trực tiếp.

2

Per-instance transaction key — a context key that carries the owning *DB, like txContextKey{db: d} in postgres.

Key transaction theo từng instance — key context mang theo *DB sở hữu nó, giống txContextKey{db: d} trong postgres.

3

Error classifier registered in init with database.RegisterClassifier, so database.Match keeps working in repositories.

Bộ phân loại lỗi đăng ký trong init bằng database.RegisterClassifier, để database.Match trong repository vẫn chạy như cũ.

4

Tracer wrapper built on tracer.BeginQuery / Finish, with the bind that matches the placeholders: sqlfmt.Bind for $1, sqlfmt.BindQuestion for ?.

Tracer wrapper dựng trên tracer.BeginQuery / Finish, với hàm bind khớp placeholder: sqlfmt.Bind cho $1, sqlfmt.BindQuestion cho ?.

5

Pass the tracer contract test — like postgres's TestExecutor_TracesEveryQuery: every query method through Executor, inside and outside a transaction, reaches the Debugger.

Vượt qua contract test của tracer — giống TestExecutor_TracesEveryQuery của postgres: mọi hàm query qua Executor, trong lẫn ngoài transaction, đều tới được Debugger.

junkit/database/mysql · tracer wrapper (database/sql)
func (w *tracedDB) ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error) {
	q := tracer.BeginQuery(ctx, query, args, sqlfmt.BindQuestion)
	res, err := w.inner.ExecContext(ctx, query, args...)
	if q != nil {
		q.Finish(tracer.SQLData{}, err)
	}
	return res, err
}
