Quick startDùng nhanh

A complete list handler. Hover an explanation to light up its lines.

Một handler danh sách hoàn chỉnh. Rê chuột vào giải thích để làm sáng các dòng tương ứng.

product_dto.go
type ListProductsRequest struct {
    pagination.Request // page, page_size, search, sort_by, sort_order
}
product_handler.go
func (h *ProductHandler) List(ctx *gin.Context) {
    var req ListProductsRequest
    if !validation.BindQuery(ctx, h.responder, h.validator, &req) {
        return // the 422 with field errors is already sent
    }
    req.SetDefaults("created_at", "desc")

    items, total, err := h.service.List(ctx.Request.Context(), req.GetLimit(), req.GetOffset())
    if err != nil {
        h.responder.Error(ctx, err)
        return
    }

    meta := pagination.NewPagination(req.Page, req.PageSize, total)
    h.responder.Pagination(ctx, 200, "products_listed", items, meta)
}

typeRequest

        
type Request struct {
    Page      int    `form:"page" binding:"omitempty,min=1" example:"1"`
    PageSize  int    `form:"page_size" binding:"omitempty,min=1,max=100" example:"10"`
    Search    string `form:"search" binding:"omitempty" example:"John"`
    SortBy    string `form:"sort_by" binding:"omitempty" example:"created_at"`
    SortOrder string `form:"sort_order" binding:"omitempty,oneof=asc desc" example:"desc"`
}


        
Standard list query parameters. Embed it in your own request struct and bind with ShouldBindQuery.

        
Các query param chuẩn cho danh sách. Nhúng vào struct request của bạn và bind bằng ShouldBindQuery.

method(*Request) GetOffset · GetLimit

        
func (r *Request) GetOffset() int32 // (Page - 1) * GetLimit(), never negative, clamped to math.MaxInt32
func (r *Request) GetLimit() int32  // PageSize clamped to [1, 100]


        
Both are safe on a Request you built by hand, without binding: GetLimit clamps the page size to 1–100 and GetOffset uses it, returning 0 for page ≤ 1. Call SetDefaults first anyway so the default page size is 10, not 1.

        
Cả hai an toàn với Request tự dựng, không qua bind: GetLimit kẹp page size trong 1–100 và GetOffset dùng nó, trả 0 khi page ≤ 1. Vẫn nên gọi SetDefaults trước để page size mặc định là 10 chứ không phải 1.

        
page has no upper bound, so a huge one (?page=3000000000) would overflow int32 into a negative OFFSET and a 500. GetOffset clamps it to math.MaxInt32 instead: the client just gets an empty page.

        
page không có giới hạn trên, nên một giá trị rất lớn (?page=3000000000) sẽ tràn int32 thành OFFSET âm và gây lỗi 500. GetOffset chặn nó ở math.MaxInt32: client chỉ nhận về một trang rỗng.

      


      

        
funcNewPagination

        
func NewPagination(page, pageSize int, totalItems int64) Pagination

        
    
          
  • page <= 0 → 1, pageSize <= 0 → 1.
  • page <= 0 → 1, pageSize <= 0 → 1.
    • 
          
  • TotalPages = ceil(total / pageSize), but never 0 — an empty list still reports 1 page.
  • TotalPages = ceil(total / pageSize), nhưng không bao giờ bằng 0 — danh sách rỗng vẫn báo 1 trang.
    • 
          
  • NextPage / PrevPage are nil (JSON null) when there is none.
  • NextPage / PrevPage là nil (JSON null) khi không có.
    • 
          
  • A page past the last one keeps its Page but gets PrevPage = TotalPages, so the client can step back to real data.
  • Trang vượt quá trang cuối giữ nguyên Page nhưng có PrevPage = TotalPages, để client lùi về dữ liệu thật.
  • It does not clamp pageSize to 100 like GetLimit. Bound requests are already ≤ 100; for a Request you built by hand, pass int(req.GetLimit()) so the metadata matches the query.
  • Hàm không kẹp pageSize về 100 như GetLimit. Request đã bind thì luôn ≤ 100; với Request tự dựng, truyền int(req.GetLimit()) để metadata khớp với query.

typePagination

        
type Pagination struct {
    Page       int   `json:"page" example:"1"`
    PageSize   int   `json:"page_size" example:"10"`
    TotalItems int64 `json:"total_items" example:"100"`
    TotalPages int   `json:"total_pages" example:"10"`
    HasNext    bool  `json:"has_next" example:"true"`
    HasPrev    bool  `json:"has_prev" example:"false"`
    NextPage   *int  `json:"next_page"`
    PrevPage   *int  `json:"prev_page"`
}

internal/features/user/dto/v1/user_dto.goListUsersRequest embeds pagination.Request; ToUserListFilter(req) copies search, GetLimit(), GetOffset() and sort order into the domain filter.ListUsersRequest nhúng pagination.Request; ToUserListFilter(req) chép search, GetLimit(), GetOffset() và sort order vào filter của domain.

      
internal/features/user/handler/v1/user_handler.goListUsers: validation.BindQuery → SetDefaults("created_at", "desc") → service → NewPagination → responder.Pagination.ListUsers: validation.BindQuery → SetDefaults("created_at", "desc") → service → NewPagination → responder.Pagination.

      
internal/features/user/repository/user_repository.goRuns ListUsersNewest or ListUsersOldest (by sort_order; LIMIT/OFFSET on the (created_at, id) index), then CountUsers for the total. A short page that is not past the end is the last one, so it already gives the total and skips the count. Not count(*) OVER(): that makes PostgreSQL read and sort every matching row to return one page, while with the index the page query can stop after OFFSET + LIMIT rows.Chạy ListUsersNewest hoặc ListUsersOldest (theo sort_order; LIMIT/OFFSET trên index (created_at, id)), rồi CountUsers để lấy tổng. Trang thiếu dòng mà không vượt quá cuối danh sách chính là trang cuối, nên đã biết tổng và bỏ qua lệnh đếm. Không dùng count(*) OVER(): nó bắt PostgreSQL đọc và sort mọi dòng khớp chỉ để trả một trang, còn nhờ index, query lấy trang có thể dừng sau OFFSET + LIMIT dòng.
